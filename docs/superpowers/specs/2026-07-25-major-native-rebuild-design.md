# 냠냠레벨업 네이티브 전면 재구축 디자인

## 문서 상태

- 상태: 사용자 승인 완료
- 승인일: 2026-07-25
- 대상: iOS 및 Android
- 출시 식별자 유지
  - iOS Bundle ID: `com.h19h29.naymnaymlevelup`
  - Android applicationId: `com.h19h29.naymnaymlevelup`

## 배경

현재 앱은 고품질 캐릭터 원화와 급식·영양·성장이라는 분명한 제품 아이디어를 갖고 있지만, 실제 사용 화면은 비슷한 카드가 반복되고 정보 우선순위가 약해 캐릭터가 주인공으로 느껴지지 않는다. 인트로의 일러스트 품질과 앱 내부의 일반적인 카드 UI 사이에도 시각적 단절이 있다.

현재 iOS는 SwiftUI 기반이지만 대형 화면 파일과 상태 객체가 커지고 있으며, Android는 약 1,900줄의 단일 `MainActivity.java`가 화면·상태·저장을 함께 담당한다. 양 플랫폼의 로컬 저장과 부모 연결 구현도 UserDefaults·CloudKit, SharedPreferences·공통 서버로 갈라져 있다. 부분적인 외형 수정만으로는 장기적으로 디자인 품질과 기능 동등성을 유지하기 어렵다.

따라서 기존 앱 위에 계속 덧붙이지 않고, 제품 경험·디자인 시스템·데이터 모델·플랫폼 구조를 함께 재설계하는 네이티브 전면 재구축을 진행한다.

## 제품 목표

최우선 목표는 다음 두 가지의 균형이다.

1. 아이가 캐릭터의 반응과 성장을 기대하며 매일 앱에 돌아온다.
2. 부모가 과장되지 않은 영양 정보와 기록 흐름을 신뢰한다.

이를 위해 아이와 부모가 같은 데이터를 사용하되 서로 다른 화면 구조와 감정 톤을 갖도록 분리한다.

## 비목표

- 아이가 먹지 않은 음식 때문에 경험치를 잃거나 죄책감을 느끼게 하지 않는다.
- 영양 정보를 질병 진단이나 의료 조언처럼 제공하지 않는다.
- 광고, 행동 추적, 무작위 보상 구매, 경쟁형 순위표를 추가하지 않는다.
- 기존 이용자의 기록을 검증 없이 삭제하거나 새 구조로 강제 변환하지 않는다.
- 새 버전 검증 전 기존 스토어 버전을 중단하지 않는다.

## 검토한 재구축 접근

### 1. 네이티브 재구축 — 채택

- iOS: SwiftUI
- Android: Kotlin 및 Jetpack Compose
- 디자인 토큰, API 계약, 데이터 의미, 모션 상태 이름, 테스트 시나리오는 공통 관리
- 플랫폼별 접근성·내비게이션·저장 기술은 각 운영체제의 표준을 사용

양쪽 화면 구현은 별도지만 스토어 안정성, 글자 확대, 접근성, 기기별 적응성과 장기 품질이 가장 좋다.

### 2. Flutter 통합 — 미채택

한 코드베이스로 시각 동등성을 맞추기 쉽지만, 이미 동작하는 SwiftUI 구현까지 모두 폐기해야 한다. 네이티브 접근성 및 플랫폼별 세부 동작을 다시 검증해야 하므로 이번 고품질 재구축의 기본 선택으로 삼지 않는다.

### 3. 공통 로직과 네이티브 UI — 미채택

Kotlin Multiplatform 등으로 도메인 로직을 공유할 수 있지만 현재 제품 규모에서는 빌드·디버깅·버전 호환 복잡성이 이점보다 크다. 대신 테스트 가능한 공통 계약 문서와 고정된 테스트 벡터로 양쪽 의미를 맞춘다.

## 전체 경험 구조

### 역할 분리

앱의 기본 진입점은 아이용 경험이다. 부모 화면은 보호자 확인을 통과한 뒤 전환한다.

아이용 하단 내비게이션:

1. `오늘`
2. `성장`
3. `도감`

부모용 하단 내비게이션:

1. `요약`
2. `기록`
3. `설정`

아이 화면에 주간 통계와 부모용 관리 기능을 섞지 않는다. 부모 화면에는 아이용 XP 연출과 수집 UI를 그대로 복제하지 않는다. 두 경험은 색과 캐릭터 정체성을 공유하지만 정보 밀도와 표현 방식은 다르게 한다.

### 아이의 핵심 순환

1. 오늘의 숲 장면에서 급식과 한 가지 주요 행동을 확인한다.
2. 메뉴마다 먹은 정도를 큰 터치 영역으로 기록한다.
3. 놓칠 수 있는 영양소를 아이가 이해할 수 있는 짧은 문장으로 확인한다.
4. 대체할 수 있는 익숙한 음식을 한두 가지 제안받는다.
5. 캐릭터가 즉시 반응하고 경험치·성장 진행도가 반영된다.
6. 성장 변화나 새 도감 항목이 있을 때만 보상 장면을 확장한다.

홈은 여러 카드가 같은 비중으로 경쟁하는 대시보드가 아니라 캐릭터, 오늘의 급식, 현재 행동이 하나의 장면으로 연결된 화면이어야 한다.

### 부모의 핵심 순환

1. 오늘 기록 완료 여부와 영양 균형 요약을 확인한다.
2. 주간 단위로 자주 놓치는 영양소와 기록 흐름을 확인한다.
3. 대체 음식과 다음 식사에서 시도할 수 있는 작은 제안을 확인한다.
4. 아이 연결, 알림, 데이터 관리와 삭제를 보호자 영역에서 수행한다.

부모 리포트는 단일 수치로 아이를 평가하지 않는다. 데이터가 부족한 날에는 점수를 만들어내지 않고 `기록 없음` 또는 `확인할 데이터가 부족해요`로 정확히 표시한다.

## 비주얼 시스템

### 채택한 세계관

비주얼 방향은 `살아있는 숲속 모험`이다.

- 아이 화면: 따뜻한 숲 배경, 유기적인 깊이, 캐릭터 중심 장면
- 부모 화면: 같은 녹색·크림 계열을 사용하되 장식과 채도를 낮춘 리포트 화면
- 앱 내부도 인트로와 같은 일러스트 세계에 속한 것처럼 보여야 한다.
- 장식 배경 위의 본문과 행동은 충분한 대비를 가진 불투명 또는 고대비 표면 위에 놓는다.

### 레이아웃 원칙

- 한 화면에는 시각적으로 가장 강한 주요 행동을 하나만 둔다.
- 같은 크기와 모양의 카드 반복을 줄인다.
- 8pt 기반 간격 체계를 사용하고 플랫폼별 안전 영역을 지킨다.
- 아이용 주요 터치 영역은 최소 48pt/dp 이상으로 설계한다.
- 장식보다 메뉴명, 상태, 주요 행동의 읽기 순서를 우선한다.
- 작은 기기와 큰 글자 환경에서도 핵심 행동이 첫 화면에서 사라지지 않아야 한다.

### 글꼴과 읽기 쉬움

이전 Apple 심사에서 지적된 읽기 어려운 서체 문제를 재발시키지 않는다.

- 본문, 버튼, 메뉴명, 영양 정보는 플랫폼 시스템 글꼴을 사용한다.
- 브랜드용 장식 서체가 필요하면 로고 또는 짧은 제목으로 범위를 제한한다.
- iOS Dynamic Type과 Android 글꼴 크기 설정을 지원한다.
- 최소 본문 크기를 임의로 줄여 레이아웃을 맞추지 않는다.
- 줄 수 제한으로 중요한 문장을 자르지 않는다.
- 본문과 배경은 WCAG AA 수준의 대비를 목표로 한다.

## 캐릭터 디자인

### 외형 방향

캐릭터 외형은 `원형 유지형`을 채택한다.

유지할 요소:

- 현재 얼굴과 몸 비율
- 주황색 털, 크림색 얼굴과 배
- 갈색 눈
- 머리의 두 잎 새싹
- 잎사귀 스카프
- 줄무늬가 있는 둥근 꼬리

개선할 요소:

- 지나치게 강한 광택과 미세 질감을 줄여 작은 화면에서도 형태가 선명하게 보이게 한다.
- 7단계 성장 캐릭터의 캔버스 크기, 기준선, 머리 높이, 발 위치를 통일한다.
- 얼굴·몸·팔·꼬리가 겹치는 부분을 리깅 가능한 구조로 다시 정리한다.
- 잠금 상태는 캐릭터 전체를 회색으로 만드는 대신 실루엣, 조명, 주변 단서로 구분해 원화의 매력을 유지한다.

`세련된 진화형`과 `과감한 게임형`은 향후 브랜드 리프레시 및 이벤트 후보로 보관한다. 방향 확인용 시안은 `docs/design-concepts/2026-07-25-major-renewal/`에 저장한다.

## 모션 시스템

### 모션 성격

기본 성격은 사용자가 선택한 `통통 튀는 게임 친구`다. 다만 모든 화면에서 계속 반복하지 않고 행동의 중요도에 따라 강도를 조절한다.

| 상태 | 목적 | 권장 길이 | 동작 |
| --- | --- | ---: | --- |
| `idle` | 살아 있는 느낌 | 5~8초 간격 | 짧은 호흡, 눈, 귀, 꼬리의 작은 움직임 |
| `tapReaction` | 터치 응답 | 0.3~0.5초 | 시선 이동, 작은 스쿼시 또는 손짓 |
| `mealSuccess` | 기록 완료 보상 | 1~2초 | 큰 점프, 표정 변화, 잎 또는 빛 반응 |
| `levelUp` | 단계 상승 | 약 3초 | 배경 변화, 캐릭터 동작, 보상 공개를 한 시퀀스로 연결 |
| `comfort` | 어려운 음식 기록 | 1~1.5초 | 고개 끄덕임, 부드러운 표정, 다음 도전 제안 |
| `reducedMotion` | 움직임 축소 | 0.2~0.3초 | 위치 이동 없이 페이드와 상태 교체만 사용 |

현재 Lottie 파일처럼 완성된 캐릭터 PNG 전체를 이동·회전하는 방식은 최종 캐릭터 모션으로 사용하지 않는다. 최소한 다음 파츠를 분리한다.

- 눈과 눈꺼풀
- 입과 볼
- 머리와 귀
- 양팔
- 몸통
- 꼬리
- 새싹
- 스카프

런타임 도구와 파일 형식은 구현 계획에서 짧은 성능 검증 후 고정하되, iOS와 Android가 같은 상태 이름과 타이밍을 사용해야 한다.

### 로고 모션

인트로 로고는 다음 순서를 유지한다.

1. `냠냠`이 먼저 올라온다.
2. `레벨업`이 이어서 올라온다.
3. 전체 로고 위로 빛이 한 번 스친다.
4. 등장 후 정지하며 반복하지 않는다.

`냠냠`과 `레벨업` 사이의 투명 영역에서 분리하고, 모든 글자 획 주변에 충분한 마스크 안전 여백을 둔다. `ㅑ`와 `ㄹ`이 잘리거나 중복되지 않아야 한다.

## 핵심 기능

### 오늘 급식

- NEIS 급식 데이터를 날짜와 학교 기준으로 조회한다.
- 조회한 급식은 로컬에 캐시한다.
- API가 실패하면 마지막 캐시, 재시도, 수동 기록 진입을 제공한다.
- 알레르기 주의 메뉴는 먹기 권유보다 안전 안내를 먼저 표시한다.
- 메뉴별 기록은 중복 탭으로 경험치가 반복 지급되지 않는 멱등 동작이어야 한다.

### 영양 안내

- 먹지 않은 메뉴에서 놓칠 수 있는 영양소를 `가능성`으로 설명한다.
- 아이용 설명은 한두 문장과 익숙한 대체 음식으로 제한한다.
- 부모용 설명에는 계산 근거, 기록 범위, 데이터가 부족한 경우를 표시한다.
- 영양소 매핑 규칙은 양 플랫폼에서 같은 입력에 같은 결과를 내도록 고정 테스트 벡터를 둔다.

### 성장과 도감

- 경험치는 긍정적인 기록과 새로운 시도에만 지급한다.
- 먹지 않음, 알레르기 회피, 기록 누락으로 경험치를 차감하지 않는다.
- 성장 단계와 잠금 해제 조건은 공통 정책 파일 또는 계약으로 관리한다.
- 도감은 수집 현황을 보여주되 무한 알림이나 불필요한 희소성 압박을 만들지 않는다.

### 부모 연결

- 아이가 보호자 초대 코드를 만들고 부모가 연결한다.
- 연결 상태, 마지막 동기화, 오류 복구를 사용자 친화적 문구로 표시한다.
- 기존 iOS CloudKit 연결은 새 공통 서버로 자동 이전 가능한지 별도 검증한다.
- 자동 이전 근거가 부족하면 로컬 기록은 보존하고 보호자 연결만 안전하게 다시 요청한다.
- 서버 주소, 업로드 키, 내부 레코드 이름을 사용자 화면에 노출하지 않는다.

## 데이터 설계

### 핵심 도메인

- `UserProfile`: 역할, 표시 이름, 학년, 학교 식별자
- `School`: NEIS 지역·학교 코드와 표시 정보
- `MealMenu`: 날짜, 메뉴, 알레르기 정보, 원본 조회 메타데이터
- `MealRecord`: 아이가 저장한 메뉴별 상태와 기록 시각
- `NutritionInsight`: 입력 기록과 규칙 버전으로 계산한 설명
- `ProgressLedger`: 경험치 발생 원인과 양을 기록하는 추가 전용 원장
- `CharacterProgress`: 현재 단계, 해제 항목, 표시 상태
- `ParentLink`: 아이·부모 연결과 권한 상태
- `SyncEnvelope`: 로컬 변경 식별자, 서버 버전, 전송 상태

경험치는 단일 누적 숫자만 저장하지 않고 원인을 가진 원장으로 계산한다. 중복 기록, 복구, 동기화 충돌에서 경험치가 반복 지급되는 것을 막는다.

### 플랫폼 저장

- iOS: Core Data
- Android: Room
- 양쪽 모두 UI와 저장소 사이에 Repository 계층을 둔다.
- 화면은 네트워크 응답을 직접 렌더링하지 않고 로컬의 확정 상태를 관찰한다.
- 서버 전송이 필요한 기록에는 고유 ID와 전송 상태를 둔다.

현재 앱의 iOS 16 최소 지원 범위를 유지하기 위해 iOS 17 이상이 필요한 SwiftData 대신 Core Data를 사용한다. 최소 지원 버전을 높이는 결정은 별도 제품 판단 없이 재구축 과정에서 임의로 수행하지 않는다.

### 오프라인 우선 흐름

1. 사용자가 식사 상태를 선택한다.
2. 로컬 트랜잭션에서 `MealRecord`와 `ProgressLedger`를 함께 저장한다.
3. UI는 즉시 캐릭터 반응과 새 진행도를 표시한다.
4. 서버 공유가 필요한 경우 동기화 대기열에 넣는다.
5. 백그라운드 동기화가 성공하면 서버 버전을 저장한다.
6. 실패하면 로컬 상태를 유지하고 부모 화면에 마지막 동기화 상태를 표시한다.

아이의 로컬 기록과 경험치는 네트워크 오류 때문에 되돌아가지 않는다.

### 동기화 충돌

- 식사 기록은 레코드 ID와 수정 시각을 사용하되 같은 기기의 재전송은 멱등 처리한다.
- 경험치 원장은 이벤트 ID로 중복을 제거한다.
- 프로필처럼 수정 가능한 값은 서버 버전과 사용자에게 보이는 최신 값을 함께 관리한다.
- 삭제는 즉시 물리 삭제하지 않고 동기화 가능한 삭제 표시를 거친다.
- 서버 스키마는 기존 출시 버전이 새 클라이언트 전환 기간에도 동작하도록 하위 호환 기간을 둔다.

## 기존 데이터 이전

첫 실행 시 이전 버전의 저장소를 읽어 새 데이터베이스로 옮긴다.

1. 기존 데이터 존재 여부와 마이그레이션 버전을 확인한다.
2. 원본을 읽어 메모리에서 검증한다.
3. 새 로컬 데이터베이스에 하나의 트랜잭션으로 기록한다.
4. 레코드 수, 경험치, 성장 단계가 원본과 일치하는지 확인한다.
5. 성공 표식을 저장한 뒤에만 새 저장소를 기본으로 사용한다.
6. 실패하면 원본을 변경하지 않고 기존 데이터 복구 안내를 표시한다.

iOS UserDefaults와 Android SharedPreferences의 실제 키 및 JSON 버전별 샘플을 고정 테스트 자료로 보관한다. CloudKit 부모 연결은 개인 기록 이전과 분리해 처리한다.

## 오류 및 빈 상태

- 학교 미설정: 학교 선택으로 바로 이동한다.
- 급식 없음: 휴일 또는 미등록 가능성을 설명하고 수동 기록을 제안한다.
- NEIS 실패: 캐시 표시 시점과 재시도 행동을 제공한다.
- 기록 저장 실패: 성공 모션을 재생하지 않고 재시도 가능한 상태를 유지한다.
- 동기화 실패: 로컬 기록이 안전하다는 점과 마지막 성공 시각을 표시한다.
- 부모 연결 만료: 새 연결을 요청하되 기존 개인 기록은 유지한다.
- 캐릭터 에셋 실패: 레이아웃을 무너뜨리지 않는 정적 기본 포즈를 표시한다.

오류 문구에는 Supabase, CloudKit, HTTP 상태 코드 등 내부 기술 용어를 노출하지 않는다.

## 아동 보호와 개인정보

- 광고 SDK와 행동 추적 SDK를 포함하지 않는다.
- 제품 품질에 필요한 진단도 개인 식사 내용과 직접 연결하지 않는 최소 이벤트만 사용한다.
- 외부 링크, 계정 연결, 데이터 내보내기와 삭제는 보호자 확인 뒤에만 제공한다.
- 수집 데이터, 목적, 보관 기간과 삭제 방법을 부모 화면과 개인정보처리방침에 일치시킨다.
- 아이에게 공개 프로필, 자유 입력 채팅, 위치 공유, 경쟁 순위를 제공하지 않는다.
- 삭제 요청은 로컬·공통 서버·연결 정보의 처리 결과를 구분해 안내한다.

## 기술 구조

### iOS

- SwiftUI 기반 기능별 모듈 또는 폴더 구조
- Core Data 모델과 Repository
- `async/await` 기반 NEIS 및 부모 동기화 클라이언트
- 앱 상태는 화면별 ViewModel과 도메인 서비스로 분리
- 접근성 값과 Reduce Motion을 디자인 시스템에서 기본 지원

### Android

- Kotlin 및 Jetpack Compose
- Room 모델과 Repository
- Coroutines·Flow 기반 비동기 처리
- Navigation Compose 기반 역할별 내비게이션
- ViewModel에서 UI 상태와 일회성 효과를 분리
- 현재 Java `MainActivity`의 기능은 새 구조로 옮긴 뒤 제거

### 공통 계약

다음 항목은 저장소의 플랫폼 중립 문서 또는 생성 가능한 데이터 파일로 관리한다.

- 색상·간격·모서리·타이포그래피 토큰
- 급식 기록 상태 이름과 의미
- 영양소 추론 규칙 버전과 테스트 입력·출력
- XP 정책과 이벤트 ID 규칙
- 캐릭터 단계·해제 조건
- 서버 요청·응답 스키마
- 오류 코드와 사용자 문구 매핑
- 캐릭터 모션 상태 이름과 권장 타이밍

공유 런타임을 도입하지 않아도 같은 계약 테스트를 양 플랫폼에서 실행해 의미 차이를 막는다.

## 품질 기준

### 기능

- 급식 조회부터 기록·성장 반영까지 오프라인 상태에서도 완료할 수 있다.
- 같은 기록을 다시 전송해도 경험치가 중복되지 않는다.
- 이전 버전의 프로필, 식사 기록, XP와 성장 단계가 보존된다.
- 부모 연결 오류가 아이의 개인 기록을 손상시키지 않는다.

### 시각 및 접근성

- 작은 iPhone, Pro Max, iPad, 소형 Android, 일반 Android 화면에서 핵심 흐름을 확인한다.
- 시스템 글자 크기를 크게 설정해도 버튼 제목과 중요한 설명이 잘리지 않는다.
- VoiceOver와 TalkBack의 탐색 순서가 시각 순서와 일치한다.
- 움직임 축소에서 주요 상태 변화를 놓치지 않는다.
- 색만으로 성공, 위험, 잠금을 구분하지 않는다.

### 성능

- 캐릭터 주요 모션은 기준 기기에서 60fps를 목표로 한다.
- 목록 스크롤과 화면 전환 중 캐릭터 디코딩으로 프레임이 멈추지 않아야 한다.
- 큰 원화는 기기 크기에 맞는 리소스로 제공하고 불필요한 전체 해상도 디코딩을 피한다.
- 앱 시작 시 네트워크 완료를 기다리지 않고 캐시된 핵심 화면을 먼저 표시한다.

### 자동 검증

- 도메인 및 영양 규칙 단위 테스트
- XP 중복 방지와 마이그레이션 테스트
- Repository 오프라인·재시도 테스트
- iOS UI 테스트와 Android Compose UI 테스트
- 주요 화면 스냅샷 또는 골든 비교
- 서버 계약 테스트
- Release 빌드 및 개인정보 선언 검증

## 출시 및 롤백 안전

- 개발은 기존 출시 코드와 분리한 브랜치에서 진행한다.
- 기존 앱은 새 앱이 베타 기준을 충족할 때까지 유지한다.
- 서버 변경은 기존 클라이언트가 계속 동작하도록 먼저 배포한다.
- 데이터 마이그레이션은 원본을 즉시 삭제하지 않는다.
- 새 클라이언트에서 치명적 문제가 발견되면 서버 기능 플래그로 새 동기화 기능을 제한할 수 있어야 한다.
- 스토어 배포와 단계적 출시 여부는 구현 완료 후 별도 승인받는다.

## 완료 기준

- 아이용 `오늘 · 성장 · 도감`과 부모용 `요약 · 기록 · 설정`이 명확히 분리된다.
- 오늘 급식 기록이 캐릭터 반응과 성장으로 자연스럽게 이어진다.
- 부모가 기록 근거와 데이터 부족 상태를 이해할 수 있다.
- 원형을 유지한 캐릭터가 상황별 파츠 애니메이션으로 반응한다.
- iOS와 Android가 같은 데이터 의미, XP 정책, 영양 결과와 핵심 문구를 사용한다.
- 기존 사용자 기록이 검증된 마이그레이션을 통해 보존된다.
- 접근성, 기기 적응성, 오프라인, 동기화, 개인정보 기준을 모두 통과한다.
