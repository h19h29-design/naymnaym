# 하루 한 번, 캐릭터의 AI 식단 해설

상태: 사용자에게 제안한 기능 방향 승인 완료. 구현 전 상세 설계 검토용.
범위: iOS·Android, 오늘 식단 전체 평가, 하루 1회 성공 생성, 기기 내 기록, 과거 평가 열람.
제외: 자유 채팅, 실제 영양사 상담, 클라우드 기록 동기화, 토스, 스토어 제출, 운영 서버 배포, 제공자 변경.

## 1. 현재 상태와 변경 목적

현재 MealNutritionCoach는 세 질문과 메뉴 선택을 제공한다. 결과는 iOS의 화면 State 및 Android 세션 StateFlow에만 남는다. 실제 AI와 기본 안내는 구분되어 있다. AI 연결은 DEBUG의 localhost 개발 설정에 한정된다.

한 번의 생성으로 식단의 특징·대표 영양소 역할·눈여겨볼 메뉴·남겼을 때 보완법을 설명한다. 캐릭터는 생각하기/설명하기 반응을 재사용한다. 새로운 이미지 생성이나 애니메이션 자산 추가는 하지 않는다.

## 2. 사용자 화면

- 오늘 화면의 캐릭터 영역에 `오늘 식단 AI 해설` 진입 버튼. 급식 상세에서도 같은 결과를 연다.
- 생성 전: `AI 영양 안내`, 오늘 생성 가능 여부, 전송 항목 고지와 명시적 동의.
- 생성 중: 기존 생각하는 동작, 진행 상태, 중복 탭 방지.
- 성공: `AI가 생성한 영양 안내`, 생성 시각, 네 개 섹션. 같은 날 다시 누르면 `오늘 평가 다시 보기`이며 AI를 다시 호출하지 않는다.
- 원본 영양 수치는 `급식 제공 영양정보`로 따로 표시한다. AI 문장에 새 수치나 반찬별 함량을 만들지 않는다.
- 과거 날짜는 저장된 평가만 열람한다. 저장 기록이 없으면 `저장된 AI 평가가 없어요`. 과거·미래 식단에 신규 호출을 허용하지 않는다.
- 급식이 없는 날에는 호출하지 않고 해당 사유를 표시한다. 준비된 캐릭터 대화는 계속 `준비된 대화`로 표시한다.
- 오류 시 `기본 영양 안내`로 복귀하며 이를 AI 평가로 저장하지 않는다.
- AI를 영양사로 지칭하거나 개인 영양 상태를 진단하지 않는다. `영양 교육용 참고 안내이며 실제 영양사·의료 상담을 대신하지 않아요`를 표시한다.

## 3. 식단 해설과 개인정보 경계

현재 집계 영양소 목록만으로 특정 메뉴를 추천할 수 없으므로 새 일일 평가 DTO를 만든다. 기존 세 질문 API와 명확하게 버전을 분리한다.

앱에서 메뉴별 대표 영양소를 기존 규칙으로 구한다. 요청에는 요청 내 익명 메뉴 ID와 영양소 ID, 원본이 확인된 식단 전체 영양량, 임시 세션/멱등 요청 ID만 담는다. 학교·메뉴 이름·식단 날짜·실제 섭취 기록·개인 식별 정보·등록 알레르기 원문은 제공자에게 보내지 않는다. 서버의 일일 제한용 인증 주체와 날짜는 제공자 요청과 분리한다.

등록 알레르기 교집합에 해당하는 메뉴는 앱에서 추천 후보에서 제외한다. 알레르기 판정 플래그도 AI에 보내지 않는다. 원본 정보가 불명확한 메뉴는 먹기 권장 후보에 넣지 않는다. 후보가 없으면 추천을 생략하고 로컬 주의 안내를 표시한다.

출력은 구성 설명, 영양소 역할, 후보 메뉴 ID와 설명(최대 2개), 일반적인 보완 안내, 판단 한계로 제한한다. 반환 ID는 요청한 후보의 부분집합이어야 한다. 앱이 ID를 실제 메뉴명에 연결한다. 추천 이유는 해당 메뉴의 알려진 대표 영양소 범위에 근거해야 한다. 검증되지 않은 근거의 추천은 노출하지 않는다.

강요·체중/외모 평가·성장 보장·질환 효과·부족/과잉 진단·음식 안전 보장은 금지한다. 대표 영양소는 메뉴 기반 추정임을 밝힌다. 없는 수량의 참조 차단, JSON/길이/안전 검증과 실패 시 기본 안내는 유지한다.

## 4. 하루 1회와 중복 방지

- 기준: 서버의 Asia/Seoul 날짜, 인증된 사용 주체당 성공 생성 1회. 현재 개발 단계는 개발 자격 증명에 귀속하며, 실제 사용자별 정책은 운영 인증 도입 전 완료로 표시하지 않는다.
- 성공 결과의 재열람은 무제한, 네트워크·AI 호출 없음. 날짜별 기록은 한 개이며 선택 식단의 식사 구분과 스냅샷을 함께 저장한다.
- 같은 날짜에 학교나 식단이 바뀌어도 추가 생성권이 생기지 않는다. 원래 기록은 보존하고 `평가 당시 식단`으로 구분한다.
- 동일 요청 ID의 동시/반복 호출은 제공자에 중복 전송하지 않는다. 일일 사용 상태는 서버 재시작 후에도 유지한다. 앱의 날짜 변경이나 화면 재진입으로 초기화하지 않는다.
- 실패는 성공 횟수로 세지 않지만 제공자 호출 비용은 생길 수 있다. 자동 재시도 없이 같은 주체의 일일 제공자 시도는 최대 3회, 기존 서버 전체 실행 한도도 유지한다.
- 답변 전달 도중 연결이 끊긴 경우 같은 요청 ID로 짧은 복구 창 안에서 동일 답변만 재전달한다. 복구용 결과는 서버 메모리에서 최대 90초 보관하고 영구 저장하지 않는다. 서버 재시작으로 복구 결과를 잃으면 추가 유료 생성을 하지 않고 실패 원인을 명확히 표시한다. 이 제한은 운영 신뢰성 검토 항목에 남긴다.
- 서버는 토큰 자체가 아닌 해시된 인증 주체, 날짜, 요청 식별자, 사용/실패 횟수와 최소 상태만 로컬 개발 저장소에 보관한다. 원본 대화·메뉴·영양량·AI 답변은 서버 영구 기록에 넣지 않는다.

## 5. 기기 내 저장과 과거 기록 안전

iOS는 기존 Rebuild Core Data 모델에, Android는 기존 Room DB에 전용 평가 엔터티를 추가한다. 기존 식사 기록·학교·성장·도감 데이터를 삭제하거나 다시 생성하지 않는다. 필수 마이그레이션 검증을 수행한다.

저장 필드: 로컬 프로필/학교 구분, 급식 날짜·식사 구분, 식단 스냅샷과 내용 지문, 생성 시각, AI 출처 및 모델/정책 버전, 검증된 구조화 결과. 이름·인증 토큰·원본 Go 키를 평가 기록에 복제하지 않는다.

기록은 앱 종료 후에도 유지하며 자동 만료하지 않는다. 기기 내 저장이므로 앱 삭제/기기 교체 시 복구를 보장하지 않는다. OS 백업 포함 여부는 별도 확인하고 클라우드 동기화가 있다고 안내하지 않는다. 평가 기록만 삭제하는 설정을 제공하되 명시적 확인 없이 다른 기록을 지우지 않는다. 로컬 기록 삭제로 서버 일일 사용 횟수를 초기화하지 않는다.

과거 평가 열람 시 당시 메뉴의 알레르기 정보와 현재 등록 알레르기를 다시 대조한다. 새로 주의 대상이 된 추천 메뉴는 숨기고 현재 경고를 우선한다. 저장된 원본은 몰래 덮어쓰지 않는다. 저장 데이터가 손상되면 해당 결과를 노출하지 않고 오류 안내를 하며 전체 DB 초기화로 복구하지 않는다.

## 6. 구현 단위

1. 공유 계약: 일일 요청/구조화 응답, 식단 지문, 시간 기준, 오류 상태 정의.
2. 서버: 별도 일일 평가 라우트, 멱등 처리, 최소 영구 사용 장부, 응답 검증. 기존 로컬 키 정책 유지.
3. iOS: Core Data 추가 모델/저장소, 일일 화면 상태, 오늘·급식 상세 통합, 동의문 변경.
4. Android: Room 마이그레이션/DAO, 일일 세션 상태, 동일 UI와 고지.
5. 안전·회귀·접근성·실제 연결 검증 및 배포 준비 재평가.

## 7. 수용 테스트

- 성공 후 앱 재실행·오프라인·다른 진입점에서 동일 평가 조회, 제공자 추가 호출 0회.
- 자정/시간대/기기 시계 변경, 동시 탭, 동일 요청 재전송, 서버 재시작, 사용 제한, 3회 실패 한도.
- 응답 전 연결 종료·90초 복구·복구 불가·로컬 저장 실패를 AI 성공 저장으로 가장하지 않음.
- 원본 수치 없는 식단, 빈 영양소, 후보 없음, 잘못된 후보 ID, 정보 부족, 출력 잘림, 안전 검증 거절.
- 생성 전/후 알레르기 변경과 과거 조회에서 추천 차단, AI에 개인 알레르기·학교·메뉴 이름이 전송되지 않음.
- 새 DB와 기존 DB 업그레이드에서 식사/성장/도감 보존, 날짜/학교별 기록 혼동 방지, 기록 삭제 범위.
- iOS/Android 큰 글자에서 AI 출처·고지·버튼·본문 접근, 캐릭터 동작 줄이기 설정 준수.
- 플랫폼 필수 단위/통합 테스트와 릴리즈 빌드 검증. 실제 Go 호출은 승인된 범위의 합성 데이터만 사용하며 별도 횟수/결과 보고.

## 8. 배포 경계

이번 단계에서 로컬 개발 기능을 구현한다. Go 일반 소비자 앱 용도 허용 여부, 운영 HTTPS·사용자 인증·영구 비용 제한, 보호자 동의·외부 처리 고지, 스토어 개인정보 항목과 AI 신고/피드백 요구사항, 독립 아동 안전 평가를 해결하기 전 AI 공개 배포는 HOLD다. 하루 1회 정책만으로 이 조건들이 해결되지는 않는다.

사용자 데이터나 비밀 설정 변경·운영 인프라 생성·배포·스토어 제출·커밋/푸시는 이번 설계 승인에 자동 포함하지 않는다.
